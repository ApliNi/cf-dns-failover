# cf-dns-failover

基于 Cloudflare DNS 的自动化故障转移与智能线路切换服务。

本项目使用原生 Golang 开发（单文件 `./main.go`，仅依赖标准库），基于 `config.yml` 配置文件运行，支持独立为 Cloudflare API 与探测请求设置网络代理，并提供支持历史稳定性、最低延迟与列表顺序的分级多策略智能切换机制。

---

## 核心特性

- **原生轻量**：单文件 `./main.go`，仅使用 Go 原生标准库，无第三方外部依赖，免去模块下载困扰，直接运行。
- **分级多策略切换模式**：支持自由组合 `stability`（历史稳定性）、`latency`（最低延迟）、`priority`（列表顺序）三大筛选策略，默认策略为 `stability,latency,priority`（**历史稳定性 > 最低延迟 > 列表顺序**）：
  - **历史稳定性（`stability`）**：基于滑动窗口（默认记录实际发生候选状态变更时的最近 30 轮测试结果，可通过 `stability_window` 调整）统计各节点在历次状态变更考验中的历史可用率，而非正常无事时每 10 秒例行探测的无意义稀释覆盖，优先选择长期运行最稳定的节点；当可用率一致且窗口尚未填满时，优先选择连续成功次数更多的节点，有效避免网络抖动导致的频繁切线以及刚恢复的假死节点被草率接入。
  - **最低延迟（`latency`）**：动态监测各就绪节点的实时 RTT 延迟，自动将 DNS 指向当前响应最快的健康节点。
  - **列表顺序（`priority`）**：按 `config.yml` 中 `list` 配置从上到下的顺序裁决优先级，越靠前优先级越高。
  - **分级筛选与平局防抖**：支持通过逗号（如 `latency,priority`）或 `>` 自定义多级裁决优先级；前一级指标相同时自动进入下一级比较；若当前活跃节点仍健康且在全部分级策略上与最佳候选平局，则保持当前节点不变，杜绝无意义的往复震荡。
- **候选节点 DNS 自动同步**：支持可选开关（`cf.sync_candidate_dns`）。开启后在软件启动时自动从候选节点的 `detect` 探测地址中提取域名，与主解析记录并发向 Cloudflare 探测该域名记录；若候选域名的当前 DNS 记录值与配置中的目标 `value` 不对等，则自动将其同步更新为 `value`，确保各候选节点的基础解析准确无误。
- **独立网络代理**：支持分别针对 Cloudflare API (`cf_proxy` / `cf.proxy`) 与目标探测 (`probe_proxy`) 配置独立的 HTTP / HTTPS / SOCKS5 代理。
- **探测重试与稳健状态机**：
  - **探测失败立即重试**：单次探测遇到网络波动或异常立即就地重试（最多 `probe_retry` 次），任意一次成功即视为健康，只有重试全部失败才计入失败；重试间附带递增退避延迟，节点宕机时不会产生高频连接风暴。
  - **统一阈值判定**：连续 `probe_count` 次探测成功判定为就绪恢复，连续 `probe_count` 次探测失败判定为离线不可用。例如设置探测次数 2、重试次数 2、循环周期 10 秒，最多需要 20 秒与 4 次探测请求确定失败。
  - **即时初始状态**：启动后各节点完成首次探测（同样支持失败就地重试）即输出「初始候选状态」，秒级感知节点全貌。
- **连接复用与生命周期管理**：内置 HTTP 连接池（Keep-Alive），所有探测与 Cloudflare API 请求显式排空响应体后归还连接池复用，避免长期运行时反复重建 TCP/TLS 连接导致连接数无限增长；空闲连接按超时自动回收。
- **精准静默日志**：
  - 仅在目标候选相对当前 DNS 指向发生变更（触发切换）时打印候选状态变更日志。
  - 启用稳定性筛选策略时，健康节点状态展示包含实时延迟与历史稳定性可用率（如 `45ms (稳定性 100%)`）。
  - DNS 切换成功时静默完成，切换失败时打印错误日志并自动重试 3 次。
- **容灾与重试**：
  - 初始化查询 DNS 记录：遇到鉴权错误立即报错退出，遇到网络或服务暂时性错误持续循环重试直至恢复。
  - DNS 切换重试：更新记录失败时自动重试 3 次，若仍失败则放弃本次修改，等待下次探测循环重试。
- **单循环防重叠**：单轮循环未结束前不触发新探测周期，避免堆积。

## 运行逻辑

1. **初始化阶段**
   - 检查 Cloudflare 中指定 `record_name` 与 `record_type` 的 DNS 记录值。
   - 若开启了候选节点 DNS 同步（`sync_candidate_dns: true`），将在启动时自动从所有候选节点的 `detect` 探测地址中提取域名，与主记录 `record_name` 并发向 Cloudflare 探测并查询记录；若某个候选域名的 DNS 记录值与配置中的 `value` 不对等，则自动将其更新为配置中的目标 `value`。
   - 若返回鉴权错误（HTTP 401/403 或 Cloudflare 认证错误码），立即退出脚本；
   - 若出现网络抖动、DNS 暂时不可达等其他错误，保持间隔循环重试，直至请求成功；
   - 成功获取记录后，确定当前 DNS 记录所指向的候选节点。

2. **首次探测（初始状态）**
   - 启动后的首次探测不遵循 `probe_count` 连续阈值，每个节点进行单次探测（若失败立即重试最多 `probe_retry` 次），并将初次探测结果计入历史稳定性采样窗口，全部完成即打印「初始候选状态」。
   - 根据探测结果与设定的分级切换策略评估最优候选；若最优候选与当前 DNS 指向不一致，立即执行候选切换。

3. **后续探测循环**
   - 每隔 `loop_time` 秒执行一次探测循环；若上一轮探测尚未结束，则跳过本次触发。
   - 并发探测配置中全部 `list.[].detect` 网址，单次探测若失败立即重试最多 `probe_retry` 次（重试间附带递增退避延迟）：
     - 探测成功：增加成功计数，失败计数清零；达到 `probe_count` 次判定为健康就绪；
     - 探测失败（全部重试均失败）：增加失败计数，成功计数清零；达到 `probe_count` 次判定为离线不可用；
     - 历史记录更新：仅在实际发生候选状态变更（节点健康状态发生翻转或目标候选触发切换）时，才将本轮测试结果计入各节点的滑动窗口（最多保留 `stability_window` 轮），正常无变更的探测轮次不写入，防止高频成功探测冲刷掉关键故障记录。
   - 所有 HTTP 请求通过内置连接池复用 Keep-Alive 连接，响应体读取完毕后显式排空关闭并归还连接池，空闲连接超时自动回收，保障长期运行连接数稳定。
   - 候选裁决与更新：
     - 按照 `switch_mode` 配置的分级策略顺序（默认 `stability,latency,priority`），在所有健康就绪节点中逐级裁决选出最优候选：
       1. **历史稳定性（`stability`）**：比较滑动窗口内的探测可用率（成功率高者胜出）；若可用率一致且窗口未满，比较连续成功次数（上限为窗口大小）。
       2. **最低延迟（`latency`）**：在稳定性相同的节点中，比较最新一次探测的 RTT 延迟，延迟低者胜出。
       3. **列表顺序（`priority`）**：在延迟亦相同的节点中，按配置列表中先后排列顺序裁决（靠前优先）。
     - 平局防抖：若当前活跃节点仍健康，且在配置的多级策略评估中与最佳候选平局，则优先保留当前活跃节点，避免无意义切线。
   - 切换触发与通知：
     - 仅当目标候选与当前 DNS 指向不一致时打印「候选状态变更, 切换到候选...」；若未发生切换则不打印状态变更日志。
     - 执行 Cloudflare PATCH 更新记录，更新失败自动重试 3 次；切换成功静默无冗余日志，切换失败输出错误原因。

## 配置说明

配置文件为 `./config.yml`（默认路径，亦可通过 `-c` 参数指定）：

```yaml
# 每隔 n 秒循环探测一次
loop_time: 10
# 探测次数: 连续几次探测成功判定为就绪 / 连续几次失败判定为不可用
probe_count: 2
# 探测失败重试次数: 一次探测如果失败就立即重试，最多尝试 n 次
probe_retry: 2
# 单次探测超时时间，秒 (若填写 >1000 则按毫秒处理)
probe_timeout: 4
# 候选节点切换模式: 支持 stability (历史稳定性) / latency (最低延迟) / priority (列表顺序)
# 支持按优先级分级筛选，使用逗号 (,) 或 > 分隔，例如 latency,priority 表示延迟相同时按列表顺序选择
# 默认值: stability,latency,priority (历史稳定性 > 最低延迟 > 列表顺序)
switch_mode: stability,latency,priority
# 历史稳定性统计的滑动窗口大小 (仅记录实际发生候选状态变更时的最近 n 轮测试结果，默认: 30，可选)
stability_window: 30
# 探测网络代理 (支持 http://, https://, socks5://)，留空表示直连或遵循系统环境变量
probe_proxy: ""
# Cloudflare API 网络代理 (支持 http://, https://, socks5://)，留空表示直连或遵循系统环境变量
cf_proxy: "http://127.0.0.1:7890"

# Cloudflare 相关的公共配置
cf:
  # API Token，建议只授予该 Zone 的 "Zone / DNS / Edit" 权限 (也可通过环境变量 CF_API_TOKEN 传入)
  api_token: ""
  # Zone ID (也可通过环境变量 CF_ZONE_ID 传入)
  zone_id: ""
  # 需要被切换指向的 DNS 记录(完整域名)
  record_name: "xxx.xxx.cc"
  # 记录类型: A / AAAA / CNAME
  record_type: "CNAME"
  # TTL, 单位秒。1 表示 Auto。proxied 为 true 时会被 Cloudflare 忽略并强制 Auto
  ttl: 60
  # 是否开启 Cloudflare CDN 代理
  proxied: false
  # 启动时是否自动探测并更新所有候选节点的 DNS 记录 (默认: false，按需开启)
  # 开启后，在软件启动时自动从候选节点的 detect 探测地址中提取域名，并发向 Cloudflare 探测该域名记录，
  # 若该域名的 DNS 记录值与配置中的 value 不对等，则自动将其更新为 value
  sync_candidate_dns: false

# 候选节点列表，按优先级从高到低排列，越靠前优先级越高
# detect: 探测地址；value: 选中时 DNS 记录指向的值 (A/AAAA 填 IP，CNAME 填域名)
list:
  - detect: "https://xx1.xxx.cc"
    value: "frp1.cc"
  - detect: "https://xx2.xxx.cc"
    value: "frp2.cc"
```

### 核心字段解释

- `switch_mode`：字符串，默认 `stability,latency,priority`。
  - **作用**：指定候选节点切换筛选策略与分级裁决顺序。支持单个策略或按逗号（`,`、`，`）或 `>`、`->` 分隔的多级策略，优先级从左往右逐级比对，前一项相同时自动进入下一项判定。
  - **支持策略及别名**：
    - `stability`（别名：`stable`、`history`、`稳定性`、`历史稳定性`）：按滑动窗口历史可用率筛选。
    - `latency`（别名：`lowest_latency`、`min_latency`、`rtt`、`延迟`、`最低延迟`）：按最新单次探测的响应延迟筛选。
    - `priority`（别名：`order`、`list`、`顺序`、`列表顺序`、`优先级`）：按配置列表顺序筛选（靠前优先）。
  - **配置示例**：
    - `stability,latency,priority`（默认）：历史稳定性最优优先；稳定性相同比延迟；延迟相同按列表顺序。
    - `latency,priority`：延迟最低优先；延迟相同时按列表顺序裁决。
    - `priority`：仅按列表配置顺序回切抢占。
- `stability_window`：整数，默认 `30`。
  - **作用**：历史稳定性采样滑动窗口大小，记录每个节点在实际发生候选状态变更（健康状态翻转或候选切换）时的最近 $N$ 轮测试结果以计算可用率。配置为 `<= 0` 时自动回退至默认值 `30`。
- `cf.sync_candidate_dns`：布尔值，默认 `false`。
  - **作用**：控制软件启动时是否自动探测并同步更新所有候选节点的 DNS 记录。
  - **提取规则**：自动从各候选节点的 `detect` 探测地址中提取其域名部分（例如从 `https://xx1.xxx.cc/path` 提取出 `xx1.xxx.cc`）。
  - **比对与更新**：在初始化阶段与 `cf.record_name` 并发向 Cloudflare 查询该域名的 DNS 记录。若查询到的 DNS 记录值与候选配置中的目标 `value` 不对等，则自动更新为 `value`。

### 环境变量支持

- `CF_API_TOKEN`：Cloudflare API 访问令牌（若设置将覆盖 `config.yml` 中的 `cf.api_token`）
- `CF_ZONE_ID`：Cloudflare Zone ID（若设置将覆盖 `config.yml` 中的 `cf.zone_id`）

## 运行方式

无需额外构建依赖，直接使用原生 Go 运行：

```bash
# 方式 1: 直接运行
go run main.go

# 方式 2: 指定配置文件
go run main.go -c /path/to/config.yml

# 方式 3: 编译为单二进制文件
go build -o cf-failover main.go
./cf-failover -c config.yml
```
